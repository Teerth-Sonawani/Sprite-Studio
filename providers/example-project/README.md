# Provider Example: Mosslight Sample Project

This folder is the provider-side companion to
[`projects/example-project`](../../projects/example-project/README.md). It does
not contain a second copy of the sample art. It shows how that project is wired
to a provider without putting credentials in tracked files.

## Why this folder exists

The sample project's art is **original procedural demo art**, created by
`scripts/build_demo_assets.py`. It was not generated by Perchance or any other
image provider. That distinction matters:

- The processing, QA, manifest and export stages are exercised end to end.
- Provider image quality is **not** demonstrated by the sample art.
- Provenance in every sample manifest records `scripted_pillow`, not an AI model.

## Provider choices for a real run

| Need | Provider | Mode | Credential |
|---|---|---|---|
| Offline pipeline test | `mock` | `offline` | None |
| Human uses the Perchance web generator | `perchance` | `manual` | None |
| Automated generation through the documented API | `perchance` | `developer_api` | `PERCHANCEAI_API_KEY` |
| The `perchance.org/api-tutorial` interface | `perchance` | `documented_tutorial` | **Unsupported**; endpoint returned HTTP 404 on 2026-11-12 |

See [`../../docs/PERCHANCE_INTEGRATION.md`](../../docs/PERCHANCE_INTEGRATION.md)
for the investigation evidence and the exact endpoints.

## Configuration

Copy `provider_config.example.yaml` to a location outside version control and
replace the paths if needed. Do **not** put the key in the YAML. The adapter reads
`PERCHANCEAI_API_KEY` from the environment.

```powershell
$env:PERCHANCEAI_API_KEY = "<your developer key>"
$env:PERCHANCE_MODE = "developer_api"

python tools/generate_asset.py health --provider perchance
python tools/generate_asset.py models --provider perchance --modality image
```

The model catalog is public. Discover model keys at runtime; do not hardcode a
key from a tutorial, because the catalog changes.

## Mapping the sample project to a provider run

The sample briefs and animation specs are reusable. A real generation run should:

1. Use `projects/example-project/assets/briefs/*.yaml` and
   `projects/example-project/style_guide.yaml`.
2. Build a prompt with `tools/build_prompt.py`.
3. Estimate cost and record the estimate.
4. Generate with `--confirm` only after the estimate is accepted.
5. Import candidates with `tools/import_generated.py` or the provider download
   path, preserving provider, mode, model key and prompt.
6. Run the same processing, QA, manifest and export steps used by the demo.
7. Keep `human_approved: false` until a human reviews the result.

## Honest limitations

- No Perchance credentials were available during the build, so no charged
  generation was run.
- Reference upload and conditioning are implemented from the documented API but
  were not exercised against a live account.
- The sample project's `provider: scripted_pillow` provenance is intentional and
  must not be rewritten as a provider result.
